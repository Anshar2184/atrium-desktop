**4.9 接管协议 v2（`p07c`）**——Guard 为 C++ 原生程序（275 KB，只依赖 USER32 / SHELL32 / KERNEL32，Per-Monitor V2 DPI）。Core 先等 Guard 的就绪握手，再在接管锁内依次执行三步：切自动隐藏 → 注册真实的底部 AppBar（56 px，工作区底边从 1904 变为 1944）→ 隐藏任务栏。每一步先检查撤销标志，再写恢复状态，再执行。恢复只有在核实任务栏可见、自动隐藏回到用户设置、工作区与接管前一致、Core 不再持有 AppBar 之后才写 `restored`。

| 场景 | 注入方式 | 恢复耗时 | 恢复者 | 结果 |
| --- | --- | --- | --- | --- |
| R1 强杀 Core | 结束进程 | 395 ms | Guard（进程退出），替已死的 AppBar 撤销保留区 | ✅ |
| R2 Core 卡死 | 主线程永久休眠 | 3.62 s（含 3 秒判定） | Guard：撤销 → 结束 Core → 恢复 | ✅ |
| R3 注册 AppBar 后崩溃 | `FailFast` | 3.07 s | Guard（错误报告使进程多存活，由心跳发现） | ✅ |
| R4 正常退出 + 两次并发手动恢复 | 4 个恢复同时发生 | 453 ms | 只执行一次，其余 3 个返回“无事可做” | ✅ |
| R5 Guard 被杀 | 结束 Guard | 439 ms | Core 先交还 AppBar，再调用 `--restore` | ✅ |
| R6 两者同时被杀 | 结束两个进程 | 1.15 s | 下次启动按残留状态恢复 | ✅ |
| R7 Guard 初始化失败 | 故障注入：控制块映射失败 | — | Guard 不发布就绪；Core 18 ms 后放弃，**全程**系统状态未变（50 次采样） | ✅ |
| R8 启动阶段停顿 | 就绪后、第一步前停 5 秒 | 2.65 s | Guard：判定卡死 → 结束 Core | ✅ |
| R9 停顿后恢复执行 | 隐藏任务栏前停 5 秒；故障注入：Guard 不结束 Core | 4.86 s | Guard 撤销并恢复；Core 恢复执行后下一步被拒绝、交还 AppBar 退出，**未再隐藏任务栏** | ✅ |
| R10 在锁内停顿后恢复执行 | 注册 AppBar 步骤持锁停 5 秒；Guard 不结束 Core | 4.97 s | 同上；Guard 等锁后恢复 | ✅ |
| R11 恢复期间 Explorer 不在 | 故障注入：找不到任务栏窗口 | Guard 8.25 s 后放弃 | Guard 写 `restore-pending`（`shell-missing`）、退出码 3；下一次恢复成功 | ✅ |
| R12 Explorer 2 秒后才出现 | 故障注入 | 2.48 s | Guard 有界重试 9 轮后完成 | ✅ |
| R13 恢复操作未生效 | 故障注入：设置自动隐藏无效 | Guard 8.28 s 后放弃 | 写 `restore-pending`（`autohide-mismatch`）；下一次恢复成功 | ✅ |
| R14 接管锁被占用超过 10 秒 | 另一进程持锁 14 秒 | 14.4 s | Guard 返回 `lock-unavailable`，**未改动**状态文件（仍为 `active`）和系统；锁释放后手动恢复成功 | ✅ |
| R15 Core 持锁时被杀 | 隐藏步骤持锁停顿时结束 Core | 371 ms | Guard 取得**废弃锁**（`abandoned=1`）后恢复 | ✅ |

判定条件：恢复后自动隐藏、任务栏可见性、工作区与测试前完全一致；恢复之后持续采样直到两个进程都退出、再观察 1.5 秒，任何一次偏离都算失败（全部为 0）；状态文件阶段与恢复者符合预期。最后恢复用户真实设置并核对。

本轮测试自身发现并修复了 3 个缺陷：
1. **Guard 没有 DPI 感知**：在 200% 缩放下读到的工作区是 `0,0,1600,952`，与 Core 记录的物理像素不一致。旧版 Guard 不核实恢复结果，所以从未暴露；新版因此全部写成 `restore-pending`。已改为 Per-Monitor V2。
2. **恢复持锁等待 Core 交还 AppBar，而恢复执行的 Core 需要同一把锁才能看到撤销**：两者互等到 8 秒上限（R9/R10 首次失败）。改为先撤销、在锁外等待 Core 退出，再持锁恢复。
3. **正常退出时 Core 等待 `--restore` 期间停止心跳**，被 Guard 误判为卡死并结束。改为等待期间继续心跳。

R11–R13 的 Explorer 缺失和操作不生效是 Guard 内的故障注入（`ATRIUM_GUARD_FAULT`），没有真的结束 Explorer。第二轮的 T1–T6（`p07b`，协议 v1、不含 AppBar）已被本表取代，原始数据保留。尚未覆盖：渲染线程卡住但 UI 线程仍有心跳、Explorer 真实重启、睡眠唤醒、系统更新、多屏。

开发中发现并修复：
1. 每个弹出窗口各建硬件设备（见 16.8），默认适配器还会唤醒独显。
2. 开始菜单测试最初误判：测试窗口位于菜单下方；以 `SwitchToThisWindow` 设置前台不可靠，改为真实点击；徽标位置随栏宽变化，每次重新读取。
3. 测试输入经过中文输入法被组合成候选词，改用 Unicode 按键输入。
4. 早期失败的测试点到了开始菜单中固定的 cmd，留下 5 个命令行窗口（按启动时间与日志逐一核对后关闭）；测试的固定项改为立即退出的 `where.exe`，并在结束时关闭测试期间新启动的 cmd / where / 计算器进程。
5. `--command` 参数尾部带空格导致 `esc` 被当成字母；命令解析去除首尾空白。
6. 网络名称取第一个已连接网络时显示为 VPN（Tailscale）；改为优先显示有互联网连接的网络。
7. 拍 README 截图时全屏背景窗口触发了全屏抑制（状态 2），通知未弹出——行为正确；截图脚本临时覆盖该状态。

未完成 / 限制：开始菜单与通知为自绘窗口，尚无 UI 自动化（屏幕阅读器）支持；托盘入口依赖 Win+B 的焦点行为；镜像 Windows 通知会与系统横幅重复（默认关闭）；点击镜像来的系统通知只能激活发送方应用，无法触发原通知内的按钮或深层链接。
