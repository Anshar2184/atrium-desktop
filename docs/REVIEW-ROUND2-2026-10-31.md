# 第二轮验证审查（2026-10-31）

审查基线：`ba6b46f`。审查对象为 `docs/VERIFICATION.md`、`docs/DECISIONS.md`、对应探测程序、原生 Guard 和已提交结果。结论：可以进入默认与系统任务栏共存的 C++ 开发切片；尚不能把接管与恢复视为生产就绪。以下代码问题来自静态审查，未在本轮重新执行破坏性故障注入。

## 需要处理的发现

### 1. [P1] 接管前没有确认 Guard 就绪，恢复与接管之间没有互斥协议

位置：`poc/Probe/RecoveryProbe.cs:45–57`；`native/guard/atrium_guard.cpp:133–146,156–160`。

Core 启动 Guard 后固定等待 300 ms，随后修改自动隐藏、隐藏任务栏。它没有确认 Guard 已打开进程句柄和心跳映射；Guard 即使无法映射心跳也继续运行，只能检测退出，不能检测卡死。Core 对 Guard 退出的检查发生在接管之后。

因此，Guard 提前失败时，Core 仍可能进入接管并在后续检查之前卡死。另一个竞态是 Core 在启动过程中停顿超过心跳阈值：Guard 开始恢复时 Core 仍可能恢复执行并继续隐藏任务栏或覆盖状态文件。恢复互斥量没有覆盖 Core 的写入与接管操作。

建议：增加可失败的 Ready 握手，确认进程身份、心跳和恢复状态可用后才允许接管；恢复开始后撤销接管权限，使用共同的事务代次/同步协议阻止 Core 继续写入。心跳映射失败应使接管失败。补测 Guard 初始化失败、启动延迟、各接管阶段暂停后恢复执行。

### 2. [P1] 未确认桌面恢复成功就写入 `restored`，导致后续重试被跳过

位置：`native/guard/atrium_guard.cpp:86–99,156–160`。

`Restore` 调用显示任务栏、恢复自动隐藏后，无条件写入 `phase=restored`；返回码只反映最后一次状态文件写入是否成功。若 Explorer 暂时不存在、Shell 操作未生效，仍会记录成功；后续恢复看到 `restored` 会直接跳过。卡死路径还在终止 Core、释放其潜在 AppBar 之前提交恢复完成，无法保证完成标记对应最终桌面状态。

建议：保留可重试的恢复中/待恢复状态；确认 Core 不再拥有接管资源，并检查可见性、自动隐藏和预期工作区后再标记完成。Shell 暂不可用时采用有界重试或留待下次恢复，不能记录成功。补测恢复期间 Explorer 不可用及恢复操作失败。

### 3. [P2] 恢复锁等待失败或超时后仍执行恢复

位置：`native/guard/atrium_guard.cpp:81–84,105–107`。

`WaitForSingleObject(mutex, 10000)` 的返回值未检查；创建互斥量失败时同样继续执行。第二个恢复进程等待超时后会在未持锁的情况下读写状态文件、修改 Shell，最后还调用 `ReleaseMutex`。所有写入共用 `path + ".tmp"`，并发执行会破坏声称的串行化保证。普通重复调用通过并不能覆盖这个分支。

建议：仅在成功获得锁（包含正确处理废弃锁）后进入临界区；超时或失败应返回明确的可重试错误，且仅由持锁者释放。增加一个持锁超过 10 秒的故障测试。

### 4. [P2] 新恢复测试未包含真实 AppBar，不能关闭完整接管事务验证

位置：`poc/Probe/RecoveryProbe.cs:30–84`；`docs/VERIFICATION.md:102–113,204`；`docs/DECISIONS.md:19–20`。

新 Core 只修改自动隐藏并隐藏系统任务栏，没有注册、定位自身 AppBar。T1–T6 验证了这一子集的恢复；先前单独的 AppBar 工作区测试不能证明 AppBar 与自动隐藏、进程卡死、Guard 恢复组合后的行为。尤其原生 Guard 注释所述“终止 Core 后释放 AppBar”的路径，当前恢复用例没有实际覆盖。

建议：保留现有通过结果，将完整事务标为部分验证；增加拥有真实 AppBar 的 Core，重跑强杀、卡死、启动失败和重复恢复，检查退出后的工作区。首轮问题 1 不宜整体标记关闭。
