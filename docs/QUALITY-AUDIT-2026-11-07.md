# Atrium 开发版质量审查与修复交接

审查日期：2026-11-07。对象：当前本地工作区，分支 `codex/design-demo-nesting`，包含尚未提交的开发改动。文中行号以本次审查时源码为准；后续请同时按函数名定位。

## 1. 当前结果与执行边界

小组件反复伸缩的外框跳动、玻璃纹理切换感已修复，用户分别确认“外框和纹理都自然了”“都自然了”。后续修复必须以这个已验收版本为基线。

本报告列出后续工作，不代表这些问题已修复，也不代表所有电脑、所有 Windows 状态均已通过验证。本轮审查没有顺手修改下面列出的产品行为。

接手者必须遵守：

- 只操作开发区及开发运行包；不动正式安装目录，不推送 GitHub，不发布版本，不改 README。
- 不降低小组件刷新频率，不改动画时长、缓动、弹性、材质参数、胶囊比例或交互布局来换性能。
- 保留实时桌面背景。暂缓桌面子窗口层级方案；不添加小组件置顶能力。
- 保留自动检查和关于页手动检查两条更新入口，保留后台下载、一次提醒、用户决定重启。
- 不扩大浏览器识别规则，不重写微信、QQ、飞书的恢复策略，不擅自增加通知兼容层。
- 不进行 Rust 重写，不引入通用服务框架、通用任务系统或大量镜像实现的测试。
- 各项独立修复、独立验收。涉及可感知效果的方案先提交对比结果，不能以“优化”为由替用户决定。

## 2. 已完成的拉伸修复

### 外框连续

`native/core/ui/surface.cpp`、`surface.h`、`render/glass_panel.h`、`glass_renderer.cpp`、`glass_renderer.h`、`bar.cpp`：

- 小组件原生窗口保持稳定的屏幕坐标，玻璃和内容通过交换链平移呈现，避免窗口位置与旧帧错配。
- 使用 `IDXGISwapChain2::SetMatrixTransform` 将位移与下一次 Present 绑定。微软文档明确说明矩阵在下一次呈现时应用：[SetMatrixTransform](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_3/nf-dxgi1_3-idxgiswapchain2-setmatrixtransform)。
- 原生宿主范围覆盖显示器，但交换链、内容及玻璃纹理仍按小组件实际需要分配，**没有分配全屏小组件纹理**。输入区域限制在当前及上一待呈现位置，避免遮挡桌面图标。
- 拖动过程中保留所需最大缓冲尺寸，手势结束后释放额外容量；待处理尺寸只保留最新值。

### 纹理连续

- 小组件背景 ROI 的原点和尺寸对齐到屏幕固定的 64 像素采样网格，保持 mip0–6 的下采样相位。
- 解决“相同桌面像素随左边界移动而改变颜色”的问题；保留实时背景、原模糊和折射参数。
- 读回结果携带提交时的 ROI 原点，字色采样使用对应坐标。
- 固定网格增加了有界的边缘预留，不能宣传成零显存代价；代价来自局部纹理，不是全屏缓冲。

## 3. 架构与覆盖范围

当前是 C++20 / Win32 / Direct3D 11 / Direct2D / DirectComposition 常驻核心，加 C# / WinUI 3 设置中心，通过命名管道通信。不是 Electron。这个分层适合当前用途，没有证据支持为了“工业化”推倒重写。

本次建立了整个源码与构建入口清单：112 个 C++、头文件、HLSL、C#、XAML 文件，合计约 31,436 行；38 个原生 `.cpp` 全部进入 CMake 构建列表，没有发现游离于构建清单的 `.cpp`。这不等于证明每个符号都有运行时用途。

| 区域 | 已检查内容 | 仍有限制 |
| --- | --- | --- |
| 核心生命周期 | 启动、退出、系统任务栏恢复、注册、设置保存、IPC | 未人为卡死系统服务或驱动 |
| 渲染 | 捕获、桌面背景、ROI/mip、读回、交换链、Surface、帧调度、圆角缓存 | 没有 GPUView / ETW 全链路性能录制 |
| 小组件 | 尺寸与位置、内容裁剪、输入区域、桌面层级、照片加载 | 新拉伸路径有实测；未重测所有编辑功能 |
| 系统集成 | 任务模型、应用目录、托盘、音量、网络、蓝牙、投屏、通知源 | 外部软件/驱动差异不能靠源码审查全覆盖 |
| 设置中心 | 预览队列、图片切换、G3 接入、控件模板、保存与关闭、更新 | 本机 dotnet 主机没有可用 SDK，重编译未完成 |
| 工程与分发 | CMake、csproj、构建脚本、GitHub 构建工作流、更新脚本、资源清单 | 未运行会生成或替换正式安装的打包/安装步骤 |

值得保留的设计：有界读回环、非阻塞 GPU Map、预览只保留最新请求、托盘图片随活跃项清理、照片解码按显示尺寸缩放、字体按包共享、WinUI 仅引用需要的组件、后台更新使用 BITS。不要把这些误判为重复模块删除。

## 4. 已确认的待修清单

P1：优先修复的功能/生命周期或明确设计契约问题。P2：确定存在的缺口，实际严重程度取决于触发条件。P3：维护性问题。静态确认与运行复现分别标注，不能将静态风险写成已发生的崩溃。

### A01 · P1 · 开发版仍可接管正式版的注册与开机启动路径

**位置：** `native/core/main.cpp:764,784`，`settings.cpp:245`，`shell/app_registration.cpp:14`，`settings/Atrium.Settings/CoreClient.cs:18,44,181`。

**证据：** 启动调用 `SetStartOnLogin`，将 Run 项指向当前 EXE；正式版和开发版路径不同就会写入。`RegisterApplication` 仅以卸载脚本和设置 EXE 是否存在判断安装包身份。完整开发包也满足条件。命名管道按用户会话命名，设置端只检查进程名，不区分安装位置。开发版重启过程中实际发生过 Run 路径改写，本轮已恢复为正式版路径。

**最小修复：** 明确开发启动身份；开发运行不修改正式注册、快捷方式、Run 项。正式安装/更新及用户切换自启时才更新其归属路径。设置中心连接核心时检查所对应的安装位置。不要默认支持两套任务栏同时运行；检测到另一实例应明确处理。

**验收：** 用独立测试注册表位置或人工审批的隔离环境，验证开发启动/退出/保存不接管正式项；正式安装及用户自启开关仍正常。不靠删除开发包内卸载脚本作为长期方案。

### A02 · P1 · 正常退出时，原生任务栏恢复仍排在可能阻塞的清理之后

**位置：** `native/core/main.cpp:903–931`，`shell/system_status.cpp:105`，`shell/app_catalog.cpp:280`，`shell/tray_model.cpp:585`。

**证据：** `status.reset()` 的线程 join 在 3 秒渲染退出保护之前；后续目录、托盘、通知源等清理也在最后的 `chrome.reset()` 之前。外部 COM / Shell 查询没有统一的可取消完成保证。当前未复现阻塞，但源码退出顺序确定存在该缺口。

**最小修复：** 退出阶段先停止再次隐藏系统界面的入口，再恢复系统任务栏/通知策略，然后清理后台资源。避免恢复后仍有 Enforce 再次隐藏；不要用每个线程强杀、长超时或新增常驻看门狗解决。

**验收：** 独立替身让一个系统查询迟迟不返回，用户请求退出后系统任务栏仍及时恢复；正常关闭、重启更新和系统注销路径均不重复隐藏。

### A03 · P1 · 控制中心查询可以重叠，过期结果会覆盖较新的状态

**位置：** `native/core/ui/control_center.cpp:218,237,259,1117,1128,1144`。

**证据：** 1.5 秒状态计时器创建 detached 查询；Radio/Audio 没有在途上限或请求代次。旧查询晚返回仍无条件覆盖状态。蓝牙/无线开关每次操作另起线程并等待 900/1500 ms；快速操作可让实际执行顺序及确认结果错位。Wi-Fi Scan 有代次过滤，但工作本身仍可重叠。

**最小修复：** 每类读取最多一个在途任务加一个最新待办，结果绑定请求代次；开关写入按用户最新意图有序执行，关闭面板后拒绝旧结果。复用现有局部模式即可，不引入通用调度框架。不要禁用正常连点或降低动画刷新频率来隐藏问题。

**验收：** 替身故意倒序完成查询，最终状态始终对应最新请求；慢查询时线程数不持续增长；正常设备响应和滑块手感不变。

### A04 · P2 · 投屏设备发现存在并发读写及 Start/Stop 竞争

**位置：** `native/core/shell/projection.cpp:31,82–98,105`。

**证据：** `Notify()` 无锁读 `hwnd/msg`，Stop 在锁内写它们。线程把 watcher 存入 State 后解锁再 Start；此时 Stop 可能看到 Created 状态而不调用 Stop，随后旧 watcher 才启动。异常分支也未检查代次就清除 searching。

**最小修复：** 通知目标在同一同步规则下读取；明确 watcher 启动、登记、停止的代次归属，失效任务必须撤销自身 watcher；异常结果不能覆盖新一轮。

**验收：** 独立替身反复 Start/Stop、在登记后延迟 Start，旧实例无残留订阅，新轮 searching 不受旧异常影响。不需要真实连接投屏设备。

### A05 · P2 · 已连接但不回复的核心会让设置请求无限等待

**位置：** `settings/Atrium.Settings/CoreClient.cs:68`，`MainWindow.xaml.cs:853,932`。

**证据：** 连接有超时，但 `_io.WaitAsync`、管道 Write/Read 没有取消期限。一个请求等待不结束，后面的预览、保存、关闭流程会排在同一个信号量后面。

**最小修复：** 给这一短请求协议添加有界等待和窗口关闭取消；超时后解除连接、释放排队请求并报告真实保存结果。不要把“没有回复”视为保存成功，也不要加入无限重连。

**验收：** 专用假管道连接后不回复，界面仍可取消并关闭；恢复连接后可正常保存；拖动设置仍采用最新值合并，不能将渲染帧节流。

### A06 · P2 · 保存设置与修改自启动不是一致的提交

**位置：** `native/core/settings.cpp:263`，`settings_server.cpp:245`，`CoreClient.cs:181`。

**证据：** 先替换 settings.json 再写 Run 项。后者失败时返回“保存失败”，但磁盘已是新设置，核心 saved 状态或设置中心 `_saved` 仍是旧值。

**最小修复：** 与 A01 一起收窄自启动写入时机，明确部分失败语义；要么恢复本次旧设置，要么明确记录哪些部分已经保存。不要新增跨系统通用事务框架。

**验收：** 对独立替身注入注册表写失败，磁盘、界面保存状态、下次启动读到的设置一致；不使用用户真实 Run 项进行失败试验。

### A07 · P2 · 背景 ROI 的屏幕外区域保留旧像素

**位置：** `native/core/render/glass_renderer.cpp:251`，`UpdateBackdrop` / `CreateSizeDependent`。

**证据：运行复现。** 源图为全白，先将 ROI 填成洋红，再将玻璃放到屏幕左上边界：有效桌面像素为 `255,255,255,255`，屏幕外 ROI 仍为 `255,0,255,255`。当前只复制交集，没有填充剩余区域；新建纹理也未初始化。模糊/折射若采到它会受历史数据影响。这与已修好的移动采样网格是不同问题。

**最小修复：** 为超出捕获边界的部分定义确定的边缘延拓，保持屏幕坐标与 64 像素 mip 相位。优先复用已有 GPU 资源，只处理必要的边缘区域；不要每帧做 CPU 全图填充，不要换静态壁纸。

**验收：** 四边和四角的独立纯色/高对比源测试不再残留旧色；再跑 MaterialProbe，mip0–6 漂移仍为零；常规位置的材质不变。

### A08 · P1（设计契约）· 设置中心部分可见裁剪仍是折线轮廓

**位置：** `settings/Atrium.Settings/ContinuousCorners.cs:200,238`，`docs/DESIGN.md` §2.3。

**证据：** AcrylicBrush、ImageBrush、ClipChildren 使用 `ApplyNativeClip`，将解析曲线上采样点通过 `CanvasPathBuilder.AddLine` 连接。底层形状模型是 G3，但这个几何裁剪路径是有限折线；单凭误差很小不能称其数学上 G3。它不同于将解析曲线直接采样到最终像素的正常栅格化。

**最小修复：** 先区分容器可见边界、子内容裁剪、整数输入区域。将可见图片/亚克力边界接入同一解析覆盖率模型；保持原材质和 XAML 内容/焦点行为。若平台能力无法同时满足，提交约束与方案供用户决定，不能改成实色、换材质或用更密折线冒充完成。

**验收：** 图片、亚克力、下拉选项、颜色浮层、焦点框的真实边界接入一致；解析模型端点证明和像素误差检查都通过。截图放大只证明观感，不代替连续性证明。Windows 外框、系统文件框、字体及第三方图标内部不在 Atrium 容器轮廓承诺内。

### A09 · P2 · 关闭一个浮层会清空同设备的公共圆角缓存

**位置：** `native/core/render/continuous_corners.h:45`，`ui/surface.cpp:594,945,977`。

**证据：** 缓存按 Direct2D device 资源域共享；每个 Surface ResetDevice/析构都按资源域整体删除。关闭通知、菜单等会使同线程同设备的其他窗口下一次重新生成掩码。

**最小修复：** 缓存失效与共享设备生命周期对齐，而不是单个 Surface 的隐藏；保留现有 64 项/4 MiB 上限，不扩大缓存来掩盖失效问题。

**验收：** 暖缓存后开关浮层，仍显示的小组件常用角掩码不被清空；设备真实重建后旧资源正确失效。测掩码创建次数，不凭内存截图判断。

### A10 · P2 · 应用图标缓存缺少失效与容量策略

**位置：** `native/core/shell/task_model.cpp:626,634,1078`，`app_catalog.h:66`，`app_catalog.cpp:338,419`。

**证据：** TaskModel 的应用/尺寸图标与名称缓存没有随已退出且未固定应用清理；目录图标缓存和 requested 表持续保留。目录图标首次失败时也把空图标存入 icons_，以后命中空结果，不会正常重试。托盘图片有 livePictures 清理，不能将它错误归入此问题。

**最小修复：** 保留固定/当前显示/在途项，清理失效身份与尺寸；失败图标在目录变化或下一次有效请求时有限重试。容量按实际像素字节约束；不要每次关闭应用都清掉所有图标导致闪烁。

**验收：** 循环多个应用和图标尺寸后缓存回到有界平台；先失败后恢复的图标能显示；已显示项不退回占位。记录缓存计数/像素字节，不能把进程所有私有内存都当作图标缓存。

### A11 · P2 · 快速切换示例照片存在过期任务回写

**位置：** `settings/Atrium.Settings/MainWindow.Photos.cs:52`，`MainWindow.Hero.cs:98,102,447`。

**证据：** 照片选择在多次 await 截图后才提交，无选择代次检查；固定材质色样每次照片变化直接 Task.Run，RenderSwatch 捕获 gen 但最终 UI 回写不检查 gen。旧任务可以晚于新任务完成并替换色样。

**最小修复：** 选择代次贯穿冻结、提交和回写；固定色样复用最新任务合并模式，旧结果不应用。保留现有 420 ms 淡出和实际材质效果，不改成立即跳切。

**验收：** 人为延迟上一张图解码，快速 A→B→C 后所有区域最终是 C；没有旧色样回闪、持续线程增加或悬挂快照。

### A12 · P2 · 更新状态损坏时，错误处理会再次读取同一损坏文件

**位置：** `settings/Atrium.Settings/ReleaseInstaller.cs:79,99,120–124`。

**证据：** ReadJson 只处理文件不存在，JSON 损坏抛异常；RunBackground catch 内再次 ReadDownload，同样异常可从错误处理分支逃逸。权限类错误也可能重复触发。

**最小修复：** 错误分支不重复依赖刚失败的读取；保留已知任务身份，明确“状态不可读”与“没有任务”的区别。不要吞掉所有错误，也不要自动清除可恢复半包或重新下载。

**验收：** 只在专门新建的临时更新目录测试截断 JSON/不可读状态，进程有可读结果，关于页可恢复；现有 BITS 任务和用户文件不受影响。

### A13 · P2 · 更新回滚只覆盖目录交换，不覆盖新程序无法启动

**位置：** `tools/Update.ps1:41–65`。

**证据：** 目录交换成功即设置 swapped；finally 删除旧目录，之后才启动新版核心和设置中心。现有回滚可以处理第二次目录重命名失败，但新版缺依赖或启动失败时旧副本已被删掉。

**最小修复：** 保留一次旧包直到本次更新启动得到明确成功信号，再清理。限定为当前更新的一份恢复点，不增加长期历史版本管理器。先定义“成功”是核心就绪及设置可启动，不以 Start-Process 返回等同成功。

**验收：** 隔离演示包中分别注入交换失败、新版启动失败，旧包可恢复且设置保留；成功后只清理本次临时目录；用户仍决定何时重启。禁止拿正式安装做故障注入。

### A14 · P2 · “只提醒一次”和“留在通知栏”跨重启不一致

**位置：** `native/core/shell/update_checker.cpp:215` 的 NotifyPrepared，`ui/notifications.cpp:119`。

**证据：** PostMessage 成功就写入 ready-notified.txt，而通知列表只在内存中；重启后标记保留、卡片消失，且不会再插入。消息入队也不等于 UI 已保存卡片。关于页仍能显示准备好的更新，这里不是下载状态丢失。

**最小修复：** 将“已弹横幅一次”与“通知中心当前可用更新卡片”分开：依据 ready 状态恢复一张静默卡片，不再次弹横幅。不需要持久化所有聊天通知。

**验收：** 下载完成只弹一次；重启后通知中心仍有一张可点击更新卡片；安装完成后消失；不产生重复计数。

### A15 · P3 · 文档与实际行为有局部漂移，部分证据引用已失效

**位置：** `docs/DESIGN.md` §0、§4、§8 小组件行；`native/core/render/shaders/glass.hlsl:2`；多处 `VERIFICATION` 注释。

**证据：** 规范仍描述小组件仅朝屏幕中间一侧的握把，而代码已支持两侧；规范称所有打断保持当前速度，但 `DesktopWidgets::Place/Glide` 使用新的 EaseOut 起点重启，并非速度连续；shader 仍引用不存在的 RENDERING-DESIGN.md。已有逐帧几何/文字布局创建，也不能将“每帧无分配”作为已实现的全局事实。

**最小修复：** 将规范中的事实与目标区分，修复断链并同步设计语言中的对应说明。不要为使文档成立而改变刚验收的动画；速度连续改造若提出，必须另行展示并验收。

**验收：** 文档链接有效、握把说明与双侧操作一致，性能约束有测量定义，数学声明覆盖范围准确；不改 README。

## 6. G3 审查结论与后续验证矩阵

原生 `corner_profile.h`、C# `CornerProfile.cs` 与 HLSL 的主轮廓公式一致。直边接点在 a>0 时具有四阶离开直线的项，曲率及弧长方向曲率变化率在接点为零；正圆没有直边接缝。这个解析论证成立，不能据此自动推出每条渲染/裁剪路径都严格符合。

| 路径 | 当前判断 | 后续动作 |
| --- | --- | --- |
| 原生连续填充、描边、Widget 内容 mask | 解析覆盖率；已验证小组件中间帧 | 保留；其它半径/描边组合做少量有代表性边界验证 |
| HLSL 独立圆角玻璃 | 同一解析边界 | 保留；不要替换为三次 Bézier 或普通圆角 API |
| C# 实色/渐变背景 | 解析掩码，经九宫格合成 | 检查分数缩放、初次加载及掩码替换时边界一致性 |
| C# 图片/亚克力/子元素裁剪 | G3 模型的折线近似 | A08，不能标记严格完成 |
| 融合/分离中的玻璃形状 | smin 连接有 C3 约束，但任意融合零等值线的正则性不能仅凭该条件保证 | 对实际使用的形状与间距检查梯度和连接；拓扑分裂瞬间若非正则要明确范围，不能空口保证所有参数 |
| 原生 HRGN 输入区域 | 整数采样区域 | 它用于命中测试，不是视觉曲线；不能要求像素整数区域拥有解析连续性，也不能据此否定实际玻璃边界 |
| Windows 外框、文件对话框、第三方图标 | 外部绘制 | 不冒充本项目已控制；不为统一外框私自替换系统 UI |

当前没有发现源码中使用非对称 CornerRadius 的实际业务调用，因此 `ContinuousCorners` 只取 TopLeft 目前记录为能力边界，不要求为假想需求增加四角配置系统。后续新增非对称需求时再处理。

## 7. 项目瘦身与模块化建议

### 可以做的小范围收敛

1. 先修 A03/A04，使系统读取的生命周期清晰；不以文件数量为目标拆模块。
2. A09/A10 后用缓存计数验证内存收益，优先减少失效重建和过期条目。
3. 在实际修改 bar 的渲染职责时，再考虑把 `RenderSession` 相关状态提取到一个私有实现单元；`bar.cpp` 约 2037 行，输入、布局、捕获与绘制协调集中。不要为满足“文件不超过 N 行”机械拆分。
4. 控制中心读写设备的状态管理与绘制分离即可；保留现有视觉布局，不创建每页一套服务对象。
5. 更新检查的两套入口是用户要求，C++ 后台与 C# 关于页有不同生命周期。共享版本/状态格式契约，不能为了去重删除一条入口或让常驻核心依赖整个设置窗口启动。

### 目前不应删除的内容

- WGC、Desktop Duplication 和壁纸降级有不同用途/兼容场景，不是看到多个捕获类就删掉。
- 托盘识别、聊天通知源、应用目录不是同一功能，不能强行合成“软件管理器”。
- C++ 与 C# 的小组件/材质示例绘制承担实际界面与设置预览的不同运行环境。应核对一致性，不直接改成静态截图。
- MiSans 三字重合计约 18.50 MiB，均属于现有设计语言；擅自删字重或裁字会改变中文显示。当前开发包约 195.5 MiB/467 文件，包含自包含运行时，不能把目录总量当作无用代码或内存占用。
- `.codex-remote-attachments/` 是用户附件，不是可直接删除的编译垃圾。`devshots/` 是忽略的验证证据，本轮没有批量删除；交接后按具体清单审批清理，不使用广泛递归删除。
- 没有发现可凭本次证据直接删除的完整产品模块，也没有发现多余的永久测试工程。没有“零死代码”的证明，接手者不能凭单次文本搜索删反射、XAML、消息回调入口。
